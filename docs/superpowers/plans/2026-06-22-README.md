# GlassBox OSS-Readiness Plan Set — Index & Cross-Plan Review

**Date:** 2026-06-22
**Scope:** Final coverage + consistency + execution-order review of the five-workstream plan set
that turns GlassBox from a medical-framed hackathon prototype into a general-purpose, self-hostable,
open-source LLM interpretability/observability tool.

This index maps every requirement in the design doc
(`docs/superpowers/specs/2026-06-22-open-source-readiness-design.md`) to the plan + task that
implements it, verifies that the shared `AppConfig` contract
(`docs/superpowers/plans/2026-06-22-appconfig-contract.md`) is used identically across all five
workstream plans, and recommends an execution order. The work decomposes into a config-backbone
gate (WS0) plus three largely-parallel feature workstreams (WS1 observability, WS2 BYO-model/SAE,
WS3 probe-pipeline/GPU) and a closing docs/CI workstream (WS4). Overall coverage is strong: every
design-doc requirement has an owning task, with only a handful of soft gaps (mostly items the design
doc itself defers or assigns to "review"). The main risks are a small number of cross-plan
field/value inconsistencies and shared-file (`config.py`, `schema.py`, `.env.example`, `app.py`,
`gpu_service.py`, `pyproject.toml`) sequencing hazards, all enumerated below.

## Recommended execution order

**WS0 → {WS1, WS2, WS3} → WS4**, matching the design doc §10 dependency graph. WS0 is the hard gate;
the three feature workstreams are largely parallelizable once `AppConfig` exists; WS4 closes out.

```
WS0 (config + hygiene + rebrand)
  │  lands AppConfig, app.state wiring, §3.2 signatures, config.example.yaml,
  │  hygiene deletions, neutral defaults
  ├─▶ WS1 (observability: drop Phoenix, rename event)
  ├─▶ WS2 (BYO model/SAE: sae.dims, sae seam)
  └─▶ WS3 (probe pipeline: auth fail-closed, agent domain, Docker)
WS1, WS2, WS3 ─▶ WS4 (README/docs/CI/issues)   [WS4 docs describe the post-WS0/WS1 state]
```

Notes that constrain the order:

- **WS0 must land first.** WS2 ("Dependency on WS0"), WS3 (Tasks 2–6 "HARD DEPENDENCY ON WS0"), and
  WS1 (config reads) all import `AppConfig`/`ProbeBuilderConfig`/`ModelConfig` and the §3.2
  signatures. WS1 can technically start before WS0 (it is written against the flat globals with a
  per-task "if WS0 already landed, swap the access path" note), but its cleanest form is post-WS0.
- **WS3 Tasks 1, 7–12 are WS0-independent** (auth fail-closed, secret cleanup, Docker, guard test)
  and may land first/in parallel; WS3 Tasks 2–6 (agent/judge config threading) require WS0.
- **WS4 Task 11 (CI) must run after WS1** — its non-GPU subset includes `test_api.py`/`test_events.py`
  (which import the WS1-renamed `IntrospectionEvent`/`build_introspection_event`) and the Phoenix test
  files WS1 deletes; Task 11 self-gates on those.
- **WS4 Task 1 (delete `docs/superpowers/`) runs last** if the executor reads plans from disk — it
  deletes the plan files themselves.
